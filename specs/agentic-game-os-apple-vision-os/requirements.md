## Introduction

This feature delivers Apple visionOS cross-platform portability for the Agentic Game OS capability layer across three repositories — `agentic-canvas-os` (invocation SSOT), `knowgrph` (shared substrate and backend utilities), and `GameXR` (frontend surfaces and multiple distinct games) — and delivers the authored specification that governs it.

The feature has two deliverables:

- **Deliverable A — Portability capability**: one shared, capability-detected portability layer so the same domain logic runs on browser Safari, iOS/iPadOS, visionOS Safari, and the native RealityKit adapter, with user-configurable 3D scenes, assets, motions and animations, offline-first continuity, and a from-0-to-1 end-to-end pipeline from Dev through a gated Prod mirror to a gated Cloudflare delivery surface.
- **Deliverable B — Authored document**: `agentic-game-os-apple-vision-os-prd-tad-adr.md` in `$GITHUB_ROOT/huijoohwee.github.io/docs/documents/`, a frontmatter-first combined PRD/TAD/ADR that specifies Deliverable A and aligns structurally with its three sibling documents without modifying them.

Both deliverables are governed by the same operating constraints: solo-operator AI-native development, typed harnesses with bounded orchestration, zero incremental infrastructure, browser-based, mobile-first, local-first, offline-first, FOSS-first, minimum-viable-maximum-value, measurable time-to-value, and explicit token and total-cost-of-ownership accounting.

### Requirement 3: Invocation Token Resolution

**User Story:** As an AI orchestrator, I want every invocation token in this feature to resolve through the Invocation_SSOT, so that no local registry, alias, or mirror competes with the dictionaries.

1. 4. 6. WHEN the Invocation_Resolver resolves any token, THE Cost_Observer SHALL record exactly one cost entry carrying the model identity, prompt token count, completion token count, and estimated cost actually observed for that resolution, recording a null model identity, token counts of zero, and an estimated cost of zero where the resolution consumes no model invocation.
7. IF a token appears more than once in the dictionary selected by its prefix, THEN THE Invocation_Resolver SHALL return a typed ambiguous-entry rejection naming the token, that dictionary path, and the count of matching entries, and SHALL return no entry.
8. IF the Invocation_Resolver receives a token whose first character is not `/`, `#`, or `@`, or whose remainder is empty, exceeds 128 characters, or contains a character outside lowercase letters, digits, `.`, and `-`, THEN THE Invocation_Resolver SHALL return a typed malformed-token rejection naming the token and the violated rule, and SHALL consult no dictionary.

### Requirement 4: Shared Substrate Ownership

**User Story:** As a solo founder, I want the Shared_Substrate to own every shared capability and backend utility, so that portability work is done once rather than once per surface.

#### Acceptance Criteria

1. THE Shared_Substrate SHALL own the shared capability set consisting of exactly the nine capabilities Immersive Input, Media, Animation, Motion Control, Flight Sim, City Builder, Camera, Game Mode, and Geo, where ownership means every module implementing that capability's behavior resides in the Shared_Substrate and is reachable by a consumer only through the Shared_Substrate declared public capability surface.
2. THE Shared_Substrate SHALL own every backend utility consumed by the Frontend_Surface, where a backend utility is any consumed module whose responsibility is not visual projection, interaction presentation, scene configuration, or a local persistence adapter as declared in Requirement 5 acceptance criterion 1.
3. THE Frontend_Surface SHALL consume each shared capability through a Shared_Substrate package or product identifier whose consumer pin record names exactly one package or product identifier, exactly one revision identifier, and exactly one artifact digest.
4. WHEN the Duplicate_Logic_Auditor scans the complete tracked source graphs declared by its schema-valid ownership manifest, THE Duplicate_Logic_Auditor SHALL resolve every static import, export, and call edge, apply every domain-state selector and canonical-output field rule, report zero Frontend_Surface duplicate-logic functions, and return that report within 120 seconds.
5. IF a Frontend_Surface function matches a declared domain-state write or canonical-output construction selector and its resolved call graph has no transitive path to that capability's exact owner export, THEN THE Duplicate_Logic_Auditor SHALL return a typed duplicate-logic violation naming the module path, export, capability, selector, and missing owner edge; an allowed adapter passes only when it maps declared fields and reaches the owner export.
6. WHEN the Frontend_Surface resolves a Shared_Substrate dependency, THE Frontend_Surface SHALL resolve exactly the revision identifier and artifact digest recorded in its consumer pin record and SHALL record the resolved values with a matched outcome.
7. IF a resolved Shared_Substrate dependency differs from its pinned revision identifier or artifact digest, or no consumer pin record exists for that dependency, THEN THE Frontend_Surface build SHALL record a typed pin-mismatch entry naming the expected value or its absence and the resolved value, mark the produced artifact as pin-mismatched, retain every produced build output unchanged, and exit with a completed status so that the operator decides whether to use the artifact.
8. IF a Deploy_Gate authorization is requested for an artifact marked pin-mismatched, THEN THE Pipeline_Controller SHALL return a typed pin-mismatch rejection naming the artifact digest and the mismatched dependency before any target-stage mutation, append only the required immutable rejection audit entry, and SHALL leave the pin-mismatched marking unchanged.
9. IF the ownership manifest is absent, empty, schema-invalid, missing or duplicating a capability ID, or the Duplicate_Logic_Auditor encounters an unreadable or truncated source, dynamic import/export, unresolved edge, or 120-second timeout, THEN THE Duplicate_Logic_Auditor SHALL return `audit-incomplete` naming every unavailable subject and reason and SHALL never report zero violations.
10. IF the Frontend_Surface requires a listed capability whose exact declared owner export cannot be resolved, THEN THE Frontend_Surface SHALL return a typed missing-capability result naming the capability, owner module/export, and consulted package or product identifier, and SHALL admit no Frontend_Surface local implementation.

### Requirement 5: Frontend Divergence and Multiple Games

**User Story:** As a solo founder, I want the Frontend_Surface to differ from the Shared_Substrate only in frontend concerns while hosting several distinct games, so that game variety costs visuals rather than forked logic.

#### Acceptance Criteria

1. THE Frontend_Surface SHALL confine its divergence from the Shared_Substrate to exactly four owned concerns — visual projection, interaction presentation, scene configuration, and local persistence adapters — such that every Frontend_Surface module is attributable to exactly one of these four concerns.
2. THE Frontend_Surface SHALL host at least three registered Game_Mode entries with mutually distinct identities, including a Flight Simulator mode, a City Building Sim mode, and an RTS-MMO mode, and SHALL admit registrations up to a declared registry capacity of at least 16 entries.
3. WHEN a Game_Mode requests registration supplying all required attributes of the single declared registration contract — unique identity, display label, entry handler, exit handler, and scene configuration — THE Frontend_Surface SHALL admit the registration without modification to any file or identifier list shared across Game_Mode entries, so that the change set for adding a Game_Mode touches only that Game_Mode's own modules plus one registration entry point.
4. IF a Game_Mode registers an identity already registered, THEN THE Frontend_Surface SHALL return a typed duplicate-identity rejection naming that identity, retain the incumbent registration unchanged, and leave the registered entry count and the active Game_Mode unchanged.
5. WHEN a Game_Mode requests registration with an updated configuration for an identity already registered, THE Frontend_Surface SHALL return a typed rejection indicating that explicit unregistration of that identity is required, retain the incumbent configuration unchanged, and admit the updated registration only after that identity has been unregistered.
6. WHEN one Game_Mode is activated while another holds the scene, THE Frontend_Surface SHALL invoke incumbent exit once before requested entry once against an unpublished staged overlay and publish exactly one overlay within 2 seconds only after entry succeeds; IF entry fails or times out, it SHALL never publish or mark the requested mode active, invoke requested exit once to quarantine staged resources and incumbent entry once to restore, return `entry-failure` on restoration success, or `activation-recovery-failure` with zero published overlays if cleanup or restoration fails.
7. IF an incumbent exit handler returns a failure, THEN THE Frontend_Surface SHALL record a typed exit-failure entry naming the incumbent identity, retain that entry for later inspection, keep the incumbent Game_Mode and its live gameplay overlay active, invoke no requested entry handler, and return without activating the requested Game_Mode.
8. WHEN two Game_Mode entries request the same shared capability, THE Frontend_Surface SHALL resolve both requests to the same Shared_Substrate implementation instance, reporting an identical capability contract identity to both Game_Mode entries and providing no per-Game_Mode variant of that capability.
9. IF a Game_Mode requests registration omitting any required attribute of the declared registration contract, THEN THE Frontend_Surface SHALL return a typed invalid-registration rejection naming the missing attribute and leave the registry unchanged.
10. IF activation is requested for a Game_Mode identity that is not registered, THEN THE Frontend_Surface SHALL return a typed unknown-identity rejection naming the requested identity, retain the currently active Game_Mode, and invoke no entry or exit handler.
11. IF a Frontend_Surface module evaluates gameplay rules, steps simulation state, or performs state transitions already provided by the Shared_Substrate, THEN THE Frontend_Surface SHALL fail its divergence check with a typed violation entry naming that module.

### Requirement 6: Capability Detection and Cross-Platform Parity

**User Story:** As a player on any Apple device, I want the highest experience my device supports without configuring anything, so that one build serves phone, tablet, headset, and desktop.

#### Acceptance Criteria

1. WHEN a surface loads, THE Capability_Detector SHALL resolve exactly one Capability_Tier from the closed Capability_Tier enumeration within 1000 milliseconds of load start, and SHALL leave every control that invokes a shared capability disabled until that resolution and its evidence source are recorded.
2. WHILE at least one declared runtime feature probe returns a determinate result, THE Capability_Detector SHALL derive the Capability_Tier from those probe results and record the evidence source as `feature-detection`; if every determinate probe value is false, THE Capability_Detector SHALL resolve `flat-fallback` with that same evidence source.
3. IF no declared runtime feature probe returns a determinate result and a user-agent string is available, THEN THE Capability_Detector SHALL resolve `flat-fallback` and record the evidence source as `user-agent`; user-agent text SHALL never elevate a tier.
4. IF no declared runtime feature probe returns a determinate result and no user-agent string is available, or the 1000-millisecond bound in acceptance criterion 1 elapses before a resolution is recorded, or every detection source raises an error, THEN THE Capability_Detector SHALL resolve the lowest member of the Capability_Tier enumeration and record the evidence source as `fallback`.
5. THE Capability_Parity_Matrix SHALL declare the closed Capability_Tier enumeration with one total order and lowest member and, for every shared capability, its supported tier set, its ordered target-specific required-probe rules as exact target, probe identifier, and required determinate boolean value records, and each target's projection status drawn from `projected` and `validated-not-projected`.
6. WHEN a shared capability is requested at a supported resolved tier, the requesting target is `projected`, and every rule for that target names a recorded determinate result equal to its required value, THE Portability_Layer SHALL execute the capability through the Shared_Substrate implementation.
7. WHEN a requested tier is unsupported, the requesting target is `validated-not-projected`, or any rule for that target is absent, indeterminate, or unequal, THE Portability_Layer SHALL return a typed capability-gap result naming the capability, target, tier, evidence source, lowest supported tier, projection status, and every unsatisfied target/probe/value rule and SHALL not execute the capability.
8. WHEN the Portability_Layer runs the same shared domain input on Browser_Runtime and on Native_Adapter at a Capability_Tier supported and marked `projected` on both with every required-probe rule satisfied, THE Portability_Layer SHALL produce canonical domain output equal on every field declared canonical for that capability.
9. WHERE a target declares no projection for a shared capability, THE Capability_Parity_Matrix SHALL record that target's projection status for that capability as `validated-not-projected` and SHALL exclude that target from the equality check in acceptance criterion 8.
10. WHEN the Capability_Detector records a resolution, THE Capability_Detector SHALL record exactly one evidence source drawn from the closed enumeration `feature-detection`, `user-agent`, and `fallback`, paired with the resolved Capability_Tier.
11. IF a recorded resolution carries zero evidence sources, two or more evidence sources, or a value outside the enumeration in acceptance criterion 10, THEN THE Capability_Detector SHALL return a typed evidence-source error payload naming the recorded value or count and carrying a required fallback TierResolution whose tier is the lowest member, evidence source is `fallback`, and probe results preserve the observations; callers SHALL use that fallback resolution while retaining the error.
12. WHILE the recorded evidence source is `user-agent`, THE Capability_Detector SHALL resolve the lowest Capability_Tier consistent with the user-agent analysis, and THE Portability_Layer SHALL treat every shared capability declared as requiring a determinate feature probe result as absent from its supported set at that tier; no counterfactual feature-detection result is inferred or recorded.

### Requirement 8: User-Configurable Scenes, Assets, Motions, and Animations

**User Story:** As a player and author, I want every 3D scene, asset, motion, and animation to be configurable and controllable by me, so that content is authored rather than hardcoded.

#### Acceptance Criteria

1. THE Scene_Manifest SHALL declare, for each Game_Mode it serves, every 3D scene, asset reference, motion profile, animation clip, camera behavior, and control profile that Game_Mode uses, where each declared entry carries an identifier of 1 to 64 characters that is unique within its category, each category holds 0 to 1000 entries, and each numeric value carries a declared minimum and maximum bound.
2. WHEN a Game_Mode loads, THE Game_Mode SHALL read every scene, asset, motion, animation, camera, and control value it applies from the validated Scene_Manifest object, and SHALL apply zero values originating from any source other than that object.
3. WHEN a user commits a Scene_Manifest value change through a control surface and the committed value satisfies the declared bounds for its field, THE Frontend_Surface SHALL apply the changed value to the live scene within 1 second measured from commit acceptance to the first rendered frame carrying the changed value.
4. WHEN the Scene_Manifest_Parser receives a Scene_Manifest text of 1 byte to 4 mebibytes conforming to the declared schema, THE Scene_Manifest_Parser SHALL return a validated Scene_Manifest object within 2 seconds.
5. IF the Scene_Manifest_Parser receives a text that violates the declared schema, exceeds 4 mebibytes, exceeds 1000 entries in any category, omits a required field, or carries a duplicate identifier within a category, THEN THE Scene_Manifest_Parser SHALL return a typed validation error naming every violated field with its expected type in one response, return no Scene_Manifest object, and leave the live scene and every Continuity_Store record unchanged.
6. THE Scene_Manifest_Printer SHALL emit the canonical JSON bytes defined in the design: NFC strings, finite numbers serialized by RFC 8785, recursively RFC-8785-sorted object keys, schema-declared array order preserved, UTF-8, and no insignificant whitespace; it SHALL produce byte-identical text for objects equal by canonical domain fields.
7. FOR ALL validated Scene_Manifest objects, THE Scene_Manifest_Parser applied to the output of THE Scene_Manifest_Printer SHALL return an object equal to the input object, where equality is field-by-field equality of every canonical domain field including collection membership and collection order.
8. FOR ALL Scene_Manifest texts accepted by THE Scene_Manifest_Parser, THE Scene_Manifest_Printer applied to the parsed object SHALL produce a text that THE Scene_Manifest_Parser accepts and parses to an object equal to that parsed object by field-by-field equality of every canonical domain field including collection membership and collection order.
9. WHEN the Shared_Substrate and the Native_Adapter each decode the same Scene_Manifest text at the same declared schema version, THE decoded canonical domain fields SHALL be equal field-by-field, including collection membership and collection order, and SHALL be equal in acceptance outcome so that a text accepted by one target is accepted by the other.
10. WHEN the Frontend_Surface applies a committed Scene_Manifest value whose canonical value differs from the active value, THE Frontend_Surface SHALL persist the resulting Scene_Manifest revision to the Continuity_Store within 2 seconds of the apply, carrying a revision index exactly one greater than the highest persisted revision index for that Scene_Manifest; WHEN the committed canonical value already equals the active value, THE Frontend_Surface SHALL return an idempotent success without applying another effect or persisting another revision.
11. IF persisting a Scene_Manifest revision to the Continuity_Store does not complete within 2 seconds or returns a failure, THEN THE Frontend_Surface SHALL restore the live scene to the last persisted revision, leave every stored Continuity_Store record unchanged, and return a typed persistence-failure error naming the field whose change was discarded and the restored revision index.
12. IF a user commits a Scene_Manifest value change whose value falls outside the declared bounds for its field, whose type differs from the declared type, or whose target field is absent from the Scene_Manifest, THEN THE Frontend_Surface SHALL reject the change, retain the current live value, persist no revision, and return a typed change-rejected error naming the field and its declared bounds or expected type.

### Requirement 9: Offline-First and Local-First Continuity

**User Story:** As a mobile player, I want to keep playing and keep my world with no network, so that connectivity is never a precondition for my own content.

#### Acceptance Criteria

1. WHILE every outbound network transport available to the runtime fails on attempt, THE Frontend_Surface SHALL complete one session cycle of open, play, commit, close, and reopen with each stage returning a success result within 10 seconds of its invocation, and, where the opened world holds no committed record, SHALL create that world at revision index 0 derived from its declared seed.
2. WHILE a session runs the play loop and no user-initiated authoring-assistance request is outstanding, THE Frontend_Surface SHALL issue zero outbound network requests and SHALL report the outbound request count observed for that play loop.
3. WHEN a user action is accepted, THE Continuity_Store SHALL append the action record and confirm that append as durable before the Frontend_Surface acknowledges the action, and this ordering SHALL hold independently of whether the acknowledgement itself is delivered.
4. WHEN a session reopens a world holding at least one committed record, THE Continuity_Store SHALL restore state equal to the highest committed revision index within 5 seconds and report that revision index together with the canonical digest it matched.
5. IF the Continuity_Store reads a record that fails schema validation, fails comparison against its recorded digest, or ends before its declared byte length, THEN THE Continuity_Store SHALL return a typed unreadable-record error naming the record and the failing check, leave every stored byte of that world byte-identical, expose an explicit reset action, and leave every other world byte-identical.
6. WHEN a second session requests write access to a world holding an unexpired write lease from a first session, THE Continuity_Store SHALL return a typed write-lease conflict naming the world and the lease-holding session, and leave the first session's records byte-identical.
7. WHEN the same seed and ordered sequence of 1 to 10,000 canonical action payloads are replayed in two fresh runtimes, THE Continuity_Store SHALL report equal lowercase SHA-256 digests of the canonical state bytes.
8. WHILE every outbound network transport fails on attempt, THE Continuity_Store SHALL queue up to 10,000 intents in first-in-first-out order, each identified by its monotone sequence and carrying canonical payload bytes plus their lowercase SHA-256 digest, and retain those exact fields and order across restarts.
9. IF an action record append fails or does not confirm durability within 2 seconds, THEN THE Continuity_Store SHALL return a typed append-failure error naming the action, withhold the acknowledgement for that action, and leave every previously committed record byte-identical.
10. IF a write lease is held by a session that has not renewed the lease for 30 seconds, THEN THE Continuity_Store SHALL treat that lease as expired and admit the next write-access request for that world.
11. IF an outbound intent is queued while the queue already holds 10,000 intents, THEN THE Continuity_Store SHALL return a typed queue-full error naming the maximum, reject the newest intent, and retain every already queued intent and its order.

### Requirement 10: From-Zero-to-One Pipeline and Deploy Gates

**User Story:** As a solo founder, I want one end-to-end pipeline from local development to gated delivery, so that a capability reaches users through a single auditable path.

#### Acceptance Criteria

1. THE Pipeline_Controller SHALL sequence the stages Dev_Runtime, Prod_Mirror, and Delivery_Surface in that order, and SHALL enter a stage only after the immediately preceding stage has recorded a successful completion outcome for the same Composite_Candidate manifest digest.
2. WHEN the Dev_Runtime stage runs, THE Pipeline_Controller SHALL start the surface through `npm run dev:apex` or `npm run dev` from a Shared_Substrate worktree whose checked-out branch is the canonical `main` branch, whose tracked-file modification count is zero, and whose untracked-file count is zero, and SHALL report a reachable local development surface within 120 seconds of invocation.
3. THE Pipeline_Controller SHALL report `delivery-verified` only after Dev_Runtime, Prod_Mirror, and Delivery_Surface have each recorded a successful completion outcome for the same Composite_Candidate manifest digest and delivery artifact digest; `delivery-verified` is pipeline evidence and is not a feature-readiness promotion.
4. THE Pipeline_Controller MAY report a Dev_Runtime-only outcome as `local-runtime-ready`, MAY report `delivery-verified` only after criterion 10.3 is satisfied, and SHALL never emit `runtime-ready` or `production-runtime-ready`; the feature completion report may emit `production-runtime-ready` only after Requirement 14 and every property, native, physical-device, mirror, and delivery gate are joined for the same Composite_Candidate manifest digest.
5. IF a Prod_Mirror write or a Delivery_Surface deployment is requested without a recorded Deploy_Gate authorization that names the operator identity, the target stage, the Composite_Candidate manifest digest, the candidate delivery artifact digest, and an authorization timestamp no older than 60 minutes, and that has not already been consumed by a prior request, THEN THE Pipeline_Controller SHALL return a typed authorization-missing rejection naming the missing, mismatched, expired, or already-consumed field before any target-stage mutation; the required rejection audit entry is not a target-stage mutation.
6. IF the Deploy_Gate authorization check returns an error or does not return a result within 10 seconds, THEN THE Pipeline_Controller SHALL perform zero retries, treat the authorization as absent, and return a typed authorization-missing rejection before any target-stage mutation; the required rejection audit entry is not a target-stage mutation.
7. WHEN the Pipeline_Controller advances a Composite_Candidate to Prod_Mirror, THE Pipeline_Controller SHALL record its exact manifest/digest, four protected repository revisions, every consumed shared pin, all three route artifact records, and the three required `GameXRNative` target artifact records before writing any Prod_Mirror byte.
8. WHEN the Pipeline_Controller deploys a Composite_Candidate to Delivery_Surface, THE Pipeline_Controller SHALL require that the recorded Prod_Mirror aggregate delivery artifact digest and the Delivery_Surface aggregate delivery artifact digest are both present and equal.
9. THE Authored_Document SHALL declare the Prod_Mirror paths and Delivery_Surface routes as boundaries that hold no world data.
10. IF the Dev_Runtime stage is requested from a worktree whose checked-out branch is not the canonical `main` branch, or whose tracked-file modification count is greater than zero, or whose untracked-file count is greater than zero, THEN THE Pipeline_Controller SHALL return a typed unclean-worktree rejection naming the offending condition and SHALL start no development surface process.
11. IF the Delivery_Surface aggregate delivery artifact digest differs from the digest recorded at the Prod_Mirror stage, or either digest is absent, THEN THE Pipeline_Controller SHALL return a typed digest-mismatch rejection naming the recorded and observed digest values, or naming the absent digest, before any mutation of the Delivery_Surface.
12. WHEN a Prod_Mirror write or a Delivery_Surface deployment reaches an outcome of completion or rejection, THE Pipeline_Controller SHALL append exactly one audit entry naming the stage, the Composite_Candidate manifest digest, the delivery artifact digest, the requested Deploy_Gate authorization identifier or `null` when none was supplied, whether that authorization was consumed, and the outcome, and SHALL retain that entry unchanged for the remainder of the pipeline run.

### Requirement 11: Source Hygiene and Root-Cause Ownership

**User Story:** As a solo founder, I want defects fixed at the owning source and hygiene enforced automatically, so that the codebase resists drift without manual review.

#### Acceptance Criteria

1. WHEN a defect is neutralized, THE fix SHALL be applied at the module whose declared responsibility covers the affected behavior, and THE change SHALL carry one regression test that fails against the module state before the fix and passes against the module state after the fix.
2. IF a change adds a downstream alias, compatibility remap, backfill, or mask for a behavior whose declared responsibility belongs to an upstream module, THEN THE change review SHALL return a typed root-source violation naming the downstream file path and the owning upstream module, and SHALL leave every authored file byte-identical to its pre-review state.
3. WHEN the Path_Portability_Auditor scans authored source, where authored source is every text file added or modified by this feature's exact declared change manifests excluding preservation-baseline Sibling_Documents, dependency directories, lockfiles, and generated build output, THE Path_Portability_Auditor SHALL report zero path literals that begin with a filesystem root and zero occurrences of an operating-system account name.
4. WHEN authored source references a repository location, THE reference SHALL express that location as `$GITHUB_ROOT` followed by a repository-relative path, and THE reference SHALL resolve to an existing location when `$GITHUB_ROOT` is set to the operator's repository parent directory.
5. WHEN the File_Size_Auditor scans authored source, THE File_Size_Auditor SHALL report zero authored files whose measured line count exceeds 600 lines.
6. THE authored source SHALL carry exactly one normalized responsibility record in each authored file using the closed comment-or-top-level-field grammar declared by Single_Responsibility_Auditor, and THE Single_Responsibility_Auditor SHALL report exact set equality between the record's declared export names and the file's statically discovered export names.
7. WHEN a legacy, stale, duplicate, or conflicting behavior is confirmed by a Duplicate_Logic_Auditor report or by a recorded operator decision, THE change SHALL remove that behavior together with every fixture and test that preserves it within the same change, and THE authored source SHALL retain zero references to the removed behavior after that change.
8. WHEN the Hardcode_Auditor runs, THE Hardcode_Auditor SHALL reject an absent, empty, schema-invalid, duplicate-ID, missing-ID, or extra-ID runtime-literal policy before source admission; SHALL resolve each policy AST consumer selector to one or more exact feature-change-set nodes; SHALL trace only direct imports, parameter bindings, destructuring, property access, and constant assignments backward to the declared source-binding selector; SHALL reject dynamic, ambiguous, cyclic, missing, or differently sourced bindings as typed unclassified-binding or hardcode violations naming the file, line, binding ID, expected source, and observed trace; and SHALL leave every authored file byte-identical on rejection.
9. IF the Path_Portability_Auditor detects one or more path literals beginning with a filesystem root or one or more operating-system account names, THEN THE Path_Portability_Auditor SHALL return a typed path-portability violation naming every offending file path and line number in one response, including the case where exactly one offending occurrence is detected.
10. IF the File_Size_Auditor measures an authored file whose line count exceeds 600 lines, THEN THE File_Size_Auditor SHALL return a typed file-size violation naming every offending file path and its measured line count, and THE change review SHALL withhold admission of the change until every named file measures 600 lines or fewer.
11. IF an authored file carries zero normalized responsibility records, carries two or more normalized responsibility records, contains an uninspectable dynamic export, or its declared and discovered export-name sets differ, THEN THE Single_Responsibility_Auditor SHALL return a typed single-responsibility violation naming the file path, record count, dynamic export, missing declared names, and unexpected discovered names as applicable.

### Requirement 12: Cost, Token Economics, and Zero-Infrastructure Bounds

**User Story:** As a solo founder, I want spend bounded and observable, so that a long session and a growing capability set both cost nothing to run.

#### Acceptance Criteria

1. WHEN a play-loop step completes without an explicit authoring-assistance request, THE Cost_Observer SHALL record exactly one cost entry within 1 second of that step completing, carrying a null model identity, a prompt token count of zero, a completion token count of zero, and an estimated cost of zero.
2. WHERE a model-bearing harness runs, WHEN one invocation completes, THE Cost_Observer SHALL record exactly one cost entry carrying the model identity, a prompt token count as a non-negative integer, a completion token count as a non-negative integer, a cache hit rate as a value from 0 through 1 inclusive, and an estimated cost expressed in one declared currency unit, including the case where every recorded count and the estimated cost are zero.
3. WHERE a harness contains a loop, THE harness SHALL declare a maximum iteration count that is an integer from 1 through 100 inclusive and exactly one circuit-breaker exit condition evaluated on every iteration.
4. WHEN this feature completes, THE count of infrastructure resources provisioned by this feature beyond those in use at feature start — hosted services, managed data stores, servers, container runtimes, scheduled jobs, and paid accounts — SHALL be zero.
5. THE Authored_Document SHALL declare, for every proposed dependency, a monthly total cost of ownership figure in one declared currency unit and a twelve-month cost assumption in that same unit, recording zero where the dependency carries no charge.
6. WHERE a paid or proprietary dependency is proposed, THE Authored_Document SHALL name at least one free and open-source alternative and the reason that alternative was set aside.
7. THE Authored_Document SHALL declare time-to-value as an integer step count of 10 or fewer, an elapsed-time ceiling of 30 minutes or fewer, and exactly one named validation method with a stated observable pass condition.
8. IF a harness loop reaches its declared maximum iteration count without satisfying its circuit-breaker exit condition, THEN THE harness SHALL exit the loop, return a typed iteration-limit result naming the harness, the declared maximum iteration count, and the iterations completed, and retain every record committed before the limit was reached.
9. IF a model-bearing harness invocation completes with no recorded cost entry, or with an absent model identity, prompt token count, completion token count, cache hit rate, or estimated cost value, THEN THE Cost_Observer SHALL return a typed cost-accounting error naming the invocation and every absent field.
10. IF the provisioned resource count defined in acceptance criterion 4 is greater than zero, THEN THE feature completion review SHALL return a typed infrastructure-violation result naming every provisioned resource and SHALL withhold the completion claim.

**User Story:** As an external agent, I want one typed read view and one bounded control route for the portability layer, so that I can inspect and drive it without scraping a user interface.

#### Acceptance Criteria

WHEN a status view is requested, THE Portability_Layer SHALL return exactly one typed status response within 1 second carrying all five fields present: the resolved Capability_Tier, the Capability_Parity_Matrix state, the registered Game_Mode identities as a list of 0 to 32 entries, the Continuity_Store restored revision index, and the Deploy_Gate state.
2. WHEN a status view is requested, THE Portability_Layer SHALL issue zero Continuity_Store writes and SHALL leave every Continuity_Store record byte-identical to its bytes recorded immediately before the request.
3. WHEN a status view is requested, THE Cost_Observer SHALL record exactly one cost entry with a null model identity, prompt and completion token counts of zero, and an estimated cost of zero.
4. WHEN a control operation is requested, THE Portability_Layer SHALL accept exactly one Control_Operation identifier drawn from its closed enumeration and validate every supplied argument against the declared schema before applying any effect.
5. IF a control operation carries an undeclared operation identifier, more than one operation identifier, an unknown argument key, or a declared operation identifier whose arguments fail schema validation, THEN THE Portability_Layer SHALL return a typed rejection naming the offending identifier or key, apply zero effects, and leave every Continuity_Store record byte-identical to its bytes recorded immediately before the request.
6. WHILE the Deploy_Gate authorization is absent, THE Portability_Layer SHALL admit only control operations whose declared scope is Dev_Runtime.
7. IF a status field is unresolved when the status view is requested, THEN THE Portability_Layer SHALL return that field carrying an explicit typed unresolved marker together with every remaining field, rather than omitting the field or failing the response.
8. IF a control operation is requested while another control operation is in progress, THEN THE Portability_Layer SHALL return a typed busy rejection naming the in-progress operation identifier, apply zero effects for the rejected request, and complete the in-progress operation unchanged.
9. IF a control operation whose declared scope is outside Dev_Runtime is requested while the Deploy_Gate authorization is absent, THEN THE Portability_Layer SHALL return a typed out-of-scope rejection naming the operation identifier and the required scope before any mutation.

### Requirement 14: Readiness Evidence and Promotion

**User Story:** As a solo founder, I want readiness stated from surfaced evidence, so that a `runtime-ready` claim is provable rather than asserted.

#### Acceptance Criteria

1. THE Authored_Document SHALL declare exactly one readiness rung for every value in the closed Readiness_Subject enumeration, drawn from the enumeration `undocumented`, `spec-complete`, and `runtime-ready`.
2. WHERE a Readiness_Subject carries the rung `runtime-ready`, THE Authored_Document SHALL cite surfaced evidence naming the exact command invoked, the Composite_Candidate manifest digest and subject-owning repository revision at which that command was invoked, the observed output including the observed exit status, and every acceptance criterion identifier of this document that the observed output satisfies.
3. WHERE a Readiness_Subject cites no evidence reference carrying all four elements required by criterion 14.2, THE Authored_Document SHALL declare that subject's rung as `spec-complete` or `undocumented`.
4. THE Authored_Document SHALL contain a readiness gap matrix with exactly one row for every value in the closed Readiness_Subject enumeration, each row naming the subject, its currently declared rung, the target rung `runtime-ready`, every blocking condition that prevents promotion, and for each blocking condition the one command whose observed output would remove it.
5. THE Authored_Document SHALL contain a validation checklist in which every entry names exactly one command, exactly one observable pass condition stated as an observed exit status or observed output text, and every acceptance criterion identifier of this document that the entry validates.
6. IF an acceptance criterion of this document has no validation checklist entry naming that criterion's identifier, THEN THE Authored_Document review SHALL return a typed coverage-gap result naming every uncovered criterion identifier in one response.
7. IF a cited evidence command is absent from the Authored_Document, is not re-invocable as written, or produces an observed output that does not satisfy every acceptance criterion identifier the citation names, THEN THE Authored_Document review SHALL return a typed evidence-invalid result naming the component, the command, and every unsatisfied criterion identifier, and THE Authored_Document SHALL declare that component's rung as `spec-complete` or `undocumented`.
8. IF either Authored_Document frontmatter rung or at least one Readiness_Subject is below `runtime-ready`, THEN THE feature completion report SHALL withhold `production-runtime-ready` and `delivered_rung` SHALL not exceed the lowest subject; only when both frontmatter rungs and every subject are exactly `runtime-ready` and every property result, physical matrix, native artifact, and criterion-10.3 `delivery-verified` receipt is valid and bound to one identical Composite_Candidate manifest digest MAY the report emit `production-runtime-ready`.
